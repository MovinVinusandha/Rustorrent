# BEP 20: Peer ID conventions - identity notes

Status: the `-BA0100-` placeholder is needed by the v0.1 tracker and peer
handshake; `docs/BEP_STATUS.md` keeps the BEP 20 row at v0.2 for the full
convention.
Source: https://www.bittorrent.org/beps/bep_0020.html
Reviewed: 2026-11-25

This is a working summary in our own words, not a copy of the BEP. Each
statement is labelled "BEP says" (checked against the BEP 20 text) or
"Our decision" (an implementation choice that the BEP does not require).
BEP 20 is a Process BEP: it records conventions, not wire requirements.

## Convention

- BEP says: the 20-byte peer ID sent in tracker requests and in the peer
  handshake has traditionally identified both the peer and the client
  implementation and version.
- BEP says: the mainline client starts with `M`, then ASCII digits for major,
  minor and tiny version separated by dashes, then random bytes.
- BEP says: many clients use a leading dash, two characters for the client,
  four ASCII digits for the version, and a trailing dash, followed by random
  bytes; `-AZ2060-` is the example.
- BEP says: the list of two-character client codes includes `AZ`, `LT`, `qB`,
  `TR`, `UT` and others, and some codes seen in the wild are still
  unidentified.
- BEP says: the remaining bytes after the version block are random.
- Our decision: the client code is `BA`, a placeholder for the working name
  `bt-app`. We checked it against every code in BEP 20's known-client table
  (which includes `BB`, `BC`, `BF`, `BG`, `BR`, `BS` and `BX`) and against
  its unidentified list (`BD`, `NP`, `wF`); `BA` appears in neither. It is
  not another client's code. When the product is named, the code is replaced
  by one derived from that name, checked the same way.
- Our decision: we do not use another client's code to get past a whitelist.
  That would misrepresent the client and is not a supported workaround.
- Our decision: the peer ID is exactly `-BA0100-` followed by 12 random
  bytes, for 20 bytes total. `0100` is version 0.1.0. The digits are bumped
  when the client version changes, not per commit.
- Our decision: the 12 random bytes come from the OS randomness source
  (`getrandom`), not from a timestamp, PID, or hash of them. They are
  generated once per process at startup and shared by every torrent.
- Our decision: the peer ID is the same in tracker announces and in the peer
  handshake. It is not persisted, so a restart gets a new ID. This is
  intentional: a stable ID across restarts would be a tracking identifier.
- Our decision: the peer ID is not configurable in v0.1. There is no
  "randomize" or "spoof" option.
- Our decision: the peer ID is never used as a tracker `key`. The key is a
  separate 32-bit value per torrent session (BEP 7 notes).
- Our decision: the user agent is `bt-app/0.1`, a placeholder held in one
  named constant and changed with the product name. It is not derived from
  the peer ID and is not configurable in v0.1.
- Our decision: the peer ID is built as a fixed 8-byte prefix plus 12 random
  bytes in a `[u8; 20]`; no string formatting, no `unwrap`, and no lossy
  conversion is involved.

## Why this shape

- Our decision: the 8-byte prefix keeps the client identifiable in tracker
  statistics, which is the convention's purpose.
- Our decision: 12 random bytes give 96 bits of entropy, far more than a
  swarm of any realistic size needs to avoid collisions.
- Our decision: one ID per process, not per torrent, matches the convention
  and keeps the handshake simple. Trackers that count distinct peers by ID
  see one client, which is correct.
- Our decision: we do not encode the platform or build in the peer ID. It
  would leak host details for no protocol benefit.

## Tests

- Our decision: the generated ID is exactly 20 bytes and starts with
  `-BA0100-`.
- Our decision: the last 12 bytes are not all zero and two generations in one
  test process differ. This is a smoke test, not a randomness proof.
- Our decision: the peer handshake encoder writes the same 20 bytes that the
  tracker announce sends.
- Our decision: a debug assertion and a unit test reject a 19-byte or 21-byte
  ID at the type boundary.
- Our decision: the ID contains only ASCII bytes, so it is safe in a
  percent-encoded query and in the 20-byte handshake field.

## Known gaps

- Our decision: many private trackers whitelist client IDs, so an unknown
  code such as `BA` may be refused. That is a product limitation, not a bug
  to work around by impersonating a listed client. A user who needs a
  whitelisted client cannot use this one until the tracker adds it.
- Our decision: no user-supplied peer ID and no per-torrent ID.
- Our decision: no anonymity mode that randomizes the client code.
- Our decision: no version negotiation; the four digits are informational
  only.
- Our decision: the ID is not persisted, so tracker-side statistics see a new
  peer after every restart.

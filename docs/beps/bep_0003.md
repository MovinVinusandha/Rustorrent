# BEP 3: Core protocol — parsing notes

Status: partial. Only bencode and v1 metainfo parsing are implemented.
Source: https://www.bittorrent.org/beps/bep_0003.html
Reviewed: 2026-11-23

This is a working summary in our own words, not a copy of the BEP. Each
statement below is labelled either "BEP says" (checked against the BEP 3 text)
or "Our decision" (an implementation choice that the BEP does not require).
Tracker HTTP fields are covered in `bep_0003_tracker.md`; tracker UDP
behaviour is BEP 15, and peer-wire behaviour remains out of scope here.

## Scope

- Our decision: this item implements bencode decoding/encoding and v1
  metainfo parsing only.
- Our decision: tracker HTTP/UDP requests, the peer wire protocol, peer IDs,
  magnet metadata exchange, BEP 12 tracker selection, BEP 27 private-torrent
  behaviour, and BEP 52 v2/hybrid torrents are not implemented in this item.
- BEP says: the specification also defines tracker requests/responses and the
  peer wire protocol; those sections are not covered by these parsing notes.

## Bencode

Grammar:

    value      := integer / string / list / dictionary
    integer    := "i" ["-"] digit+ "e"
    string     := length ":" byte*
    list       := "l" value* "e"
    dictionary := "d" (string value)* "e"

- BEP says: a string is a base-ten byte length, a colon, then exactly that many
  bytes.
- BEP says: an integer is `i`, an optional minus sign, base-ten digits, then
  `e`.
- BEP says: `i-0e` is invalid.
- BEP says: leading zeros are invalid, except for `i0e`.
- BEP says: integers have no size limitation.
- Our decision: integers are capped at `i64`; larger values are rejected.
- BEP says: a list is `l`, zero or more bencoded values, then `e`.
- BEP says: a dictionary is `d`, then alternating keys and values, then `e`.
- BEP says: dictionary keys must be strings.
- BEP says: dictionary keys must appear in sorted order, compared as raw
  strings rather than alphanumerically.
- Our decision: dictionary keys are compared as raw bytes in ascending order.
- Our decision: duplicate dictionary keys are invalid in every decoding mode.
- Our decision: the decoder has two key-order modes:
  - `Strict`: keys must be strictly increasing in raw byte order. This is used
    by the bencode tests and the fuzz round-trip target.
  - `Lenient`: keys may appear in any order, but duplicate keys are still
    rejected. This is used by `MetaInfo::parse`.
- Our decision: no whitespace or trailing bytes are accepted after the
  top-level value.
- Our decision: in `Strict` mode, a successful decode must re-encode to
  exactly the input bytes.
- Our decision: in `Lenient` mode, a successful decode need not re-encode to
  the input bytes, because dictionary keys may be unsorted. This is why the
  info-hash uses the original byte span rather than a re-encoding.
- Our decision: at the bencode layer, strings are arbitrary byte strings.
  UTF-8 is enforced only where the metainfo format says a field contains text.

### Implementation limits

- Our decision: the following limits are named constants in
  `engine::bencode` and apply to every decode unless a test supplies smaller
  values through `decode_with_limits`.

| Limit | Constant | Value |
|---|---|---|
| Total input | `MAX_INPUT_BYTES` | 32 MiB |
| One string | `MAX_STRING_BYTES` | 16 MiB |
| Integer literal | `MAX_INT_BYTES` | 20 bytes (sign + 19 digits) |
| Nesting depth | `MAX_DEPTH` | 64 |
| Items per list/dict | `MAX_CONTAINER_ITEMS` | 100,000 |
| Values in one parse | `MAX_NODES` | 1,000,000 |

- Our decision: these caps prevent a length read from the input, or a deeply
  nested container, from causing unbounded allocation.
- Our decision: invalid input is rejected with a typed error; it is never
  repaired or partially accepted.
- Our decision: `Value` equality ignores source spans. Two values are equal
  when their kinds and contents are equal, even if they came from different
  byte offsets. The encoder, not equality, is responsible for reproducing the
  original bytes.

## Metainfo

- BEP says: a metainfo file is a bencoded dictionary.
- BEP says: the top-level `announce` key maps to the tracker URL.
- BEP says: the top-level `info` key maps to a dictionary.
- BEP says: all strings in a `.torrent` file that contain text must be UTF-8.
- Our decision: `announce` is optional, so trackerless torrents parse.
- Our decision: if `announce` is missing, empty, the wrong type, or not valid
  UTF-8, it becomes `None`. This is not an error.
- Our decision: `announce-list` is parsed as tracker tiers from BEP 12,
  although BEP 3 does not define it. Invalid entries are dropped and empty
  tiers are dropped. This is not an error.
- Our decision: unknown top-level and unknown info keys are ignored.

### Info dictionary

- BEP says: `name` maps to a UTF-8 string that is the suggested file or
  directory name.
- BEP says: `piece length` maps to the number of bytes in each piece.
- BEP says: pieces are fixed-size except possibly the last piece, which may be
  truncated.
- BEP says: `pieces` maps to a string whose length is a multiple of 20; each
  20-byte group is the SHA-1 hash of the corresponding piece.
- BEP says: `piece length` is almost always a power of two.
- Our decision: `piece length` is not required to be a power of two.
- BEP says: the info dictionary has either `length` or `files`, but not both
  and not neither.
- BEP says: in the single-file case, `length` is the file length in bytes.
- BEP says: in the multi-file case, the files are concatenated in the order
  they appear in `files`.
- BEP says: `files` is a list of dictionaries with `length` and `path`.
- BEP says: `path` is a list of UTF-8 subdirectory names; the last component
  is the file name.
- BEP says: a zero-length `path` list is an error case.
- Our decision: `name` is required and must be a safe single path component.
- Our decision: exactly one of `length` and `files` is required.
- Our decision: `length` and every file `length` must be non-negative.
- Our decision: `files` must be non-empty.
- Our decision: every `path` list must be non-empty and every component must be
  a valid UTF-8 string.
- Our decision: file lengths are summed with checked arithmetic; overflow is an
  error.
- Our decision: duplicate complete file paths are rejected. Duplicate
  detection is exact, not case-insensitive; case-insensitive and
  post-sanitization collision handling belongs to the storage layer.
- Our decision: `info.private` is parsed now. It is `true` only when the value
  is the integer `1`; every other value becomes `false`. BEP 3 does not define
  this key; it is a BEP 27 field and its behaviour is later work.
- Our decision: if `info` contains `meta version` equal to `2` and has no
  `pieces` key, parsing returns `Error::UnsupportedV2`. This is a BEP 52 field,
  not a BEP 3 field.
- Our decision: a hybrid torrent with `meta version` equal to `2` and a valid
  `pieces` key is parsed as v1.

## Info-hash

- BEP says: the info-hash is the 20-byte SHA-1 digest of the bencoded `info`
  value from the metainfo file.
- BEP says: that value is a substring of the metainfo file.
- BEP says: the hash is of the encoded form found in the file; for a fully
  validated input it is identical to decoding, extracting the info dictionary,
  and encoding it again.
- BEP says: clients must either reject invalid metainfo files or extract the
  substring directly; they must not decode and re-encode invalid data to
  compute the hash.
- Our decision: the decoder records the exact byte range of every value. The
  info-hash is SHA-1 over the recorded `info` range, including its leading `d`
  and trailing `e`.
- Our decision: the implementation never re-encodes the info dictionary to
  compute the info-hash.

## Path safety

- BEP says: `name` and `path` contain text and must be UTF-8.
- BEP says: a zero-length `path` list is an error case.
- Our decision: the metainfo parser rejects only the following in `name` and
  in each `path` component:
  - an empty component;
  - `.`;
  - `..`;
  - `/`;
  - NUL and ASCII control characters.
- Our decision: the parser does not reject backslashes, Windows drive
  prefixes, Windows reserved device names, other Windows-invalid characters,
  or trailing dots/spaces. Those are sanitized per operating system in the
  storage layer (roadmap item 3).
- Our decision: the storage layer is also responsible for case-insensitive
  collision detection and for detecting collisions that appear only after
  sanitization.
- Our decision: a complete relative path is the torrent `name` followed by the
  components in `files[].path` (or just `name` for a single file).
- Our decision: duplicate complete paths are rejected by the metainfo parser
  using exact string comparison.

## Piece validation

- BEP says: the `pieces` string length is a multiple of 20.
- BEP says: each 20-byte group is the SHA-1 hash of the piece at the
  corresponding index.
- Our decision: `piece length` must be greater than zero.
- Our decision: `piece length` is capped at `MAX_PIECE_LENGTH` (64 MiB);
  larger values are rejected with `Error::PieceLengthTooLarge`.
- Our decision: the number of hashes must equal
  `ceil(total_length / piece_length)`, or zero when the total length is zero.
- Our decision: extra or missing piece hashes are rejected.
- Our decision: a zero-length single-file torrent with an empty `pieces`
  string is accepted; it has zero piece hashes.

## Errors

- Our decision: all invalid input produces a typed `thiserror` error.
- Our decision: the parser does not panic, does not truncate silently, and
  does not use `unwrap` or `expect` on untrusted data.
- Our decision: bencode errors are propagated by the metainfo parser.

## Test vectors

- Our decision: the metainfo tests build two small torrents in code and
  hardcode their info-hashes.
- Our decision: the hardcoded hashes are computed independently with Python
  `hashlib.sha1` over the exact raw `info` bytes. The command is recorded in a
  test comment.
- Single-file fixture: `file.txt` holding `hello` (5 bytes), piece length 4,
  so two piece hashes. Info-hash:
  `269d5c49e062c6b94788155e71659e472c752c0d`.
- Multi-file fixture: directory `dir` with `a.txt` (1 byte) and `b.txt`
  (2 bytes), piece length 4, so one piece hash. Info-hash:
  `6fea2a866e2f72f21dc5c1047b9af51d3f3d3a12`.
- Our decision: tests also cover the `MAX_PIECE_LENGTH` boundary,
  `Error::UnsupportedV2`, and zero-length single-file torrents with no piece
  hashes.

## Known gaps

- Our decision: invalid UTF-8 in `name` or `path` is rejected for now.
- Our decision: `.utf-8` keys and legacy text encodings are not supported in
  this item. They are listed as a known gap in `docs/BEP_STATUS.md` and in the
  v0.2 roadmap.
- Our decision: `info.private` is parsed, but private-torrent behaviour
  (disabling DHT/PEX/LSD) is later BEP 27 work.

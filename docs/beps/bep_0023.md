# BEP 23: Compact peer lists - decoding notes

Status: planned for v0.1 (HTTP response decoding; UDP is compact by design).
Source: https://www.bittorrent.org/beps/bep_0023.html
Reviewed: 2026-11-25

This is a working summary in our own words, not a copy of the BEP. Each
statement is labelled "BEP says" (checked against the BEP 23 text) or
"Our decision" (an implementation choice that the BEP does not require).

## Formats

- BEP says: a tracker may return peers as a packed string instead of a
  bencoded list, to reduce response size and tracker memory and CPU use.
- BEP says: in the original list form each peer is a dictionary with
  `peer id`, `ip` and `port`; the peer ID is 20 bytes and the `ip` value may be
  a domain name of up to 255 bytes.
- BEP says: in the compact form each peer is exactly 6 bytes: a 4-byte IPv4
  address followed by a 2-byte port, both in network byte order.
- BEP says: the compact value uses the same `peers` key, but the value is a
  bencoded string instead of a bencoded list.
- BEP says: the peer ID is not present in the compact form; the lack of a peer
  ID has not caused problems.
- BEP says: `compact=1` in the announce URL advises the tracker that the
  client prefers compact peers, and `compact=0` advises the original format.
- BEP says: the `compact` key is advisory only; the tracker may return either
  format, so clients must support both.
- BEP says: a client that requests compact peers must still accept the list
  form.
- Our decision: the HTTP announce always sends `compact=1`. We never send
  `compact=0`.
- Our decision: the decoder accepts `peers` as either a bencoded string or a
  bencoded list, regardless of the value we sent. A tracker that ignores
  `compact=1` still works.
- BEP says (BEP 15): UDP announces do not carry a `compact` parameter; BEP 15
  defines one wire format, and it is the compact one.
- Our decision: a `peers` value that is neither a string nor a list is a
  malformed response. The announce fails with
  `TrackerError::MalformedResponse` rather than silently returning an empty
  swarm.

## Compact decoding

- Our decision: a 6-byte stride is used only for the `peers` string and only
  on IPv4. The 18-byte `peers6` string is BEP 7, not BEP 23.
- Our decision: the string length is divided by 6. Complete records are
  decoded; a trailing partial record is ignored and counted in a
  `malformed_peer_records` warning. No slice ever runs past the string.
- Our decision: a zero-length string is valid and means zero peers.
- Our decision: each record is converted to `SocketAddrV4`. Port 0, the
  unspecified address, multicast and broadcast are dropped. Loopback, private
  and link-local addresses are kept because LAN swarms are legitimate; see
  the target policy in ADR 0003 for tracker targets, which is separate.
- Our decision: decoded peers are deduplicated by socket address, keeping the
  first occurrence, and the result is capped at 200 peers per response.

## List decoding

- BEP says: the list form carries `peer id`, `ip` and `port` per peer.
- Our decision: `peer id` is optional and ignored. We do not use it for
  anything and do not require it.
- Our decision: `ip` and `port` are required. A peer entry with a missing or
  wrong-typed field is dropped individually; the rest of the list is kept.
- Our decision: `ip` must be a literal IPv4 or IPv6 address. A hostname is
  dropped, because resolving tracker-supplied hostnames would let a tracker
  direct our DNS traffic and widen the SSRF surface. The drop is counted.
- Our decision: `port` must be an integer in `1..=65535`. Port 0 and
  out-of-range values are dropped.
- Our decision: the same invalid-address rules apply as in the compact form
  (port 0, unspecified, multicast, broadcast), plus the IPv6 rules, dedup and
  the 200-peer cap.
- Our decision: a list entry that is not a dictionary is skipped. A `peers`
  list with more than 200 valid entries is truncated after the cap.
- Our decision: an empty list is valid and means zero peers.

## Errors and limits

Our decision:

| Condition | Result |
|---|---|
| `peers` missing | zero peers, warning |
| `peers` wrong type | `TrackerError::MalformedResponse` |
| compact length not a multiple of 6 | decode complete records, warn |
| list entry missing `ip`/`port` | drop entry, warn |
| list `ip` is a hostname | drop entry, warn |
| port 0 or out of range | drop entry, warn |
| more than 200 peers | truncate, warn |

- Our decision: warnings are counters plus a fixed message, never the raw
  tracker bytes. A tracker response can contain a passkey in a URL and must
  not reach a log.
- Our decision: the whole response body is already capped at 1 MiB before
  decoding, so the peer section is bounded before any per-peer work.

## Tests

- Our decision: a compact vector with two peers, one of them `0.0.0.0:0`,
  proves that one peer is kept and one dropped.
- Our decision: a 13-byte compact string proves that two records are decoded
  and the trailing byte is ignored.
- Our decision: a list vector with an IPv4 literal, an IPv6 literal, a
  hostname, a missing port, and port 0 proves per-entry filtering.
- Our decision: a `peers` value of integer type, and a missing `peers` key,
  prove the malformed and empty cases.
- Our decision: a 201-entry compact string proves the 200-peer cap.
- Our decision: duplicate addresses in both formats prove dedup.
- Our decision: `tracker_http_response` fuzz target feeds arbitrary bytes to
  the response and peer decoders and asserts no panic and no unbounded
  allocation.

## Known gaps

- Our decision: no peer ID is available from compact responses, so we never
  key peer state on it.
- Our decision: no hostname peers from the list form; this is stricter than
  BEP 23 and is a deliberate SSRF decision.
- Our decision: no `peers6` in this note; see BEP 7.
- Our decision: no response compression. A tracker that returns gzip without
  being asked is treated as malformed.

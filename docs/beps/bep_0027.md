# BEP 27: Private torrents - announce notes

Status: the tracker rule (private flag, one active tracker, same-host redirect,
peer drop on switch) is planned for v0.1. Enforcement for DHT, PEX, LSD and
web seeds lands with those components.
Source: https://www.bittorrent.org/beps/bep_0027.html
Reviewed: 2026-11-25

This is a working summary in our own words, not a copy of the BEP. Each
statement is labelled "BEP says" (checked against the BEP 27 text) or
"Our decision" (an implementation choice that the BEP does not require).

## Flag and scope

- BEP says: a private tracker restricts access to the torrents it tracks; a
  torrent with restricted access is a private torrent.
- BEP says: a metainfo file denotes a private torrent with the key-value pair
  `private=1` in the `info` dictionary.
- BEP says: the pair is inside `info`, so it is covered by the info-hash and
  cannot be changed without changing the torrent identity.
- Our decision: `MetaInfo.private` is `true` only for the integer `1`.
  `private=0`, a missing key, or any other type is public. This matches the
  existing parser and is deliberately strict.
- Our decision: the flag is read once at metainfo load and is immutable for
  the torrent session. There is no per-torrent override in v0.1.

## Tracker use

- BEP says: a client that obtains a metainfo file with `private=1` MUST only
  announce to the private tracker.
- BEP says: it MUST only initiate connections to peers returned from the
  private tracker.
- BEP says: when a private torrent lists multiple trackers in `announce-list`,
  each peer MUST use only one tracker at a time.
- BEP says: the peer MUST switch trackers only when the current tracker fails.
- BEP says: when switching, the peer MUST disconnect from all current peers
  and connect only to peers provided by the new tracker.
- BEP says: the rationale is that DHT, PEX and LSD would let an intruder learn
  peer addresses and join a swarm that the private tracker is trying to
  restrict, and that dropping connections on a switch prevents a peer from
  bridging two swarms.
- Our decision: a private torrent never uses the BEP 12 tier fan-out. Its
  `announce-list` is flattened, shuffled once, and used as an ordered
  candidate list with exactly one active tracker.
- Our decision: the first candidate is active until it fails. A failure means
  a transport error, a timeout, or a tracker `failure reason`; a success
  resets nothing in the candidate order and keeps the tracker active. The
  state machine resets its failure counter separately (ADR 0003).
- Our decision: on failure, the next candidate becomes active. The failed
  tracker is not retried before the rest of the list has been tried.
- Our decision: switching trackers drops every peer connection and every peer
  candidate learned from the previous tracker, before the first announce to
  the new tracker. Downloaded pieces and verified progress are kept.
- Our decision: a private torrent with no usable tracker URL fails with
  `TrackerError::NoUsableTracker` and is not announced anywhere. There is no
  fallback to DHT.
- Our decision: the tracker URL list is not extended from a redirect for a
  private torrent. A redirect is followed only when the target has the same
  host, with the same effective port unless the scheme upgrades from `http`
  to `https` (then the default https port is allowed); a cross-host redirect
  fails the announce. Hosts are compared with a trailing dot normalized, and
  ports after default-port normalization. The policy is
  `RedirectPolicy::SameHostOnly`, carried in `AnnounceRequest` and enforced by
  the transport. The redirected URL is never added to the candidate list.
- Our decision: `trackerid` returned by the active tracker is kept for that
  tracker only and is dropped when the active tracker changes.

## Other peer sources

- BEP says: the four ways a peer can learn about a swarm are trackers, DHT,
  PEX and LSD; using any of them other than the private tracker subverts the
  tracker's access control.
- Our decision: in v0.1 the session-level `private` guard and the tracker
  rules exist. DHT (v0.1), PEX, LSD and web seeds (v0.2) are separate
  components; when each lands, it must consult the guard and refuse to run
  for a private torrent. The guard is enforced at the session level, not only
  by not starting the components, so a future component cannot opt in by
  accident.
- BEP says: the client must only initiate connections to peers returned from
  the private tracker.
- Our decision: web seeds (BEP 19) are also disabled for a private torrent.
  BEP 27 predates BEP 19 and does not name web seeds, but they are a peer
  source that the tracker did not return, so the same rule applies.
- Our decision: incoming connections are still accepted. BEP 27 restricts
  outgoing peer discovery, not listening. An incoming peer that knows the
  info-hash is treated as part of the swarm.
- Our decision: a future peer source (for example a second DHT mode or a
  local peer cache) must check `private` before returning any candidate.

## Interaction with BEP 12

- BEP says (BEP 12): `announce-list` is a list of lists of URLs, grouped
  into tiers.
- Our decision: for a private torrent the tier boundaries are ignored. The
  URLs are concatenated in document order and then shuffled once. The 32-URL,
  8-tier and 4-per-tier caps are applied at parse time before flattening.
- Our decision: the "move successful tracker to front" rule is not needed,
  because only one tracker is ever active; the active index is kept instead.
- Our decision: a private torrent with a single `announce` URL and no
  `announce-list` behaves exactly like a one-candidate private torrent.

## Tests

- Our decision: a private torrent with three trackers proves that only one
  tracker is contacted per round, and that the next one is contacted only
  after the active one fails.
- Our decision: a fake tracker returns one peer; after a forced switch, the
  test proves that the old peer connection is closed before the first
  announce to the new tracker, and that the old peer is not re-added.
- Our decision: a private torrent with DHT, PEX, LSD and web seeds enabled in
  the session config proves that none of them produces or accepts a peer.
- Our decision: a private torrent with an empty tracker list fails with
  `TrackerError::NoUsableTracker` and makes no network request.
- Our decision: `private=0`, a missing `private` key, and `private` as a
  string are all public.
- Our decision: a private torrent with a redirect proves that a cross-host
  target is rejected, that the target is not added to the candidate list, and
  that exactly one request is made.
- Our decision: a private torrent whose `announce-list` has more than 4 URLs
  in one tier proves that the 4-per-tier cap is applied before flattening.

## Known gaps

- Our decision: no way to mark a torrent private at runtime; the flag comes
  only from metainfo.
- Our decision: no per-tracker passkey management beyond the URL itself.
- Our decision: no audit that the private tracker is the one the user
  intended; the metainfo list is trusted for tracker selection, as BEP 27
  assumes.
- Our decision: incoming connections are not restricted to peers the tracker
  knows, because the protocol cannot prove that.

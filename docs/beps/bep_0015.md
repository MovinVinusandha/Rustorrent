# BEP 15: UDP tracker protocol - announce notes

Status: planned for v0.1 (announce only).
Source: https://www.bittorrent.org/beps/bep_0015.html
Reviewed: 2026-11-25

This is a working summary in our own words, not a copy of the BEP. Each
statement is labelled "BEP says" (checked against the BEP 15 text) or
"Our decision" (an implementation choice that the BEP does not require).
Scrape and BEP 41 extensions are out of scope.

## Transport and framing

- BEP says: the tracker protocol runs over UDP.
- BEP says: all values are sent in network byte order (big endian).
- BEP says: packets must not be assumed to be exactly a certain size, because
  future extensions could increase the size.
- BEP says: before announcing or scraping, the client has to obtain a
  connection ID with a connect request.
- BEP says: the connection ID exists to stop source-address spoofing; the
  tracker verifies it on the announce.
- BEP says: a client can use a connection ID until one minute after it has
  received it, and trackers should accept it until two minutes after it was
  sent.
- Our decision: one connected UDP socket per tracker announce attempt. The
  socket is connected to the checked tracker address, so the kernel drops
  datagrams from other sources.
- Our decision: the connection ID is reused within one announce attempt. We do
  not keep a cross-announce connection-ID cache in v0.1; the next announce
  reconnects. This is allowed but not required by the BEP.
- Our decision: receive buffer is 4096 bytes. A datagram larger than that is
  truncated by the kernel; the peer cap below means the wanted peers are in
  the first part of the packet. A trailing partial peer record is ignored.
- Our decision: no scrape and no BEP 41 extension negotiation in v0.1.

## Timeouts and retransmission

- BEP says: if a response is not received after `15 * 2^n` seconds, the client
  should retransmit the request, where `n` starts at 0 and is increased up to 8
  (3840 seconds) after every retransmission.
- BEP says: it is necessary to re-request a connection ID when it has expired.
- BEP says: the worked example retransmits at 15, 45 and 105 seconds
  (cumulative).
- Our decision: one 105-second deadline per attempt, measured from the first
  datagram. Waits are 15, 30 and 60 seconds, so sends are due at 0, 15 and 45
  seconds. Every datagram, connect or announce, counts as one of the three
  sends. A reconnect replaces the announce for that slot and does not reset
  the deadline.
- Our decision: a `stopped` announce uses a 2-second deadline and no retries,
  on UDP as on HTTP, instead of the 105-second normal-attempt deadline.
- Our decision: before every send, if the connection ID is at least 50 seconds
  old, send a new connect instead of the announce. 50 seconds is our decision;
  BEP 15 allows use until 60 seconds after receipt, and a tracker silently
  ignores an expired ID. The new ID is used once the connect response arrives.
- Our decision: DNS resolution gets 5 seconds and is outside the 105-second UDP
  budget. A resolve timeout fails the attempt.
- Our decision: UDP `connect` is a local operation after DNS; there is no
  separate connect timeout. The first receive wait is the connect timeout.
- Our decision: when the 105-second deadline is reached, the attempt fails with
  `Timeout`; the socket is dropped.

## Connect

- BEP says: a connect request is 16 bytes:

  | Offset | Size | Field | Value |
  |---|---|---|---|
  | 0 | 8 | protocol_id | `0x41727101980` |
  | 8 | 4 | action | `0` (connect) |
  | 12 | 4 | transaction_id | chosen by the client |

- BEP says: a connect response is 16 bytes:

  | Offset | Size | Field | Value |
  |---|---|---|---|
  | 0 | 4 | action | `0` (connect) |
  | 4 | 4 | transaction_id | echo of the request |
  | 8 | 8 | connection_id | opaque value for later requests |

- BEP says: after receiving the packet, check that it is at least 16 bytes,
  that the transaction ID matches, and that the action is connect.
- Our decision: the transaction ID is 32 bits from the OS randomness source.
  It is generated fresh for every connect and every announce request.
- Our decision: a connect response shorter than 16 bytes is a malformed
  response. Bytes beyond 16 are ignored (forward compatibility).
- Our decision: an action or transaction-ID mismatch is a malformed response;
  the packet is ignored and the receive wait continues until its deadline.

## Announce

- BEP says: an IPv4 announce request is 98 bytes:

  | Offset | Size | Field | Value |
  |---|---|---|---|
  | 0 | 8 | connection_id | from the connect response |
  | 8 | 4 | action | `1` (announce) |
  | 12 | 4 | transaction_id | chosen by the client |
  | 16 | 20 | info_hash | raw v1 info-hash |
  | 36 | 20 | peer_id | our peer ID |
  | 56 | 8 | downloaded | bytes downloaded |
  | 64 | 8 | left | bytes still needed |
  | 72 | 8 | uploaded | bytes uploaded |
  | 80 | 4 | event | `0` none, `1` completed, `2` started, `3` stopped |
  | 84 | 4 | IP address | `0` means the source address |
  | 88 | 4 | key | client key |
  | 92 | 4 | num_want | `-1` means the tracker default |
  | 96 | 2 | port | our TCP listen port |

- BEP says: an announce response is at least 20 bytes:

  | Offset | Size | Field |
  |---|---|---|
  | 0 | 4 | action (`1`) |
  | 4 | 4 | transaction_id |
  | 8 | 4 | interval (seconds) |
  | 12 | 4 | leechers |
  | 16 | 4 | seeders |
  | 20 + 6*n | 4 | IPv4 address |
  | 24 + 6*n | 2 | TCP port |

- BEP says: after receiving the packet, check that it is at least 20 bytes,
  that the transaction ID matches, and that the action is announce.
- BEP says: do not announce again until `interval` seconds have passed or an
  event has occurred.
- BEP says: most trackers only honour the `IP address` field under limited
  circumstances.
- Our decision: send the request as exactly 98 bytes. There is no padding and
  no extension field in v0.1.
- Our decision: `IP address` is always `0`; we do not try to publish a
  different address.
- Our decision: `num_want` is 50 for `started`, `completed` and periodic
  announces, and 0 for `stopped`. This matches the HTTP `numwant` rule. The
  decoder still accepts up to 200 peers.
- Our decision: `key` is a 32-bit value generated once per torrent session and
  reused for HTTP and UDP announces, and for IPv4 and IPv6 announces of that
  torrent. See BEP 7 notes.
- Our decision: `port` is the actual TCP listen port supplied by the session.
  Port 0 is rejected before a request is built.
- Our decision: `event` is `2` (started) on the first announce, `1`
  (completed) once when the download finishes, `3` (stopped) on pause,
  removal or shutdown, and `0` otherwise. See the announce state machine in
  ADR 0003.
- Our decision: a response of exactly 20 bytes is valid and means zero peers.
- Our decision: a response whose peer section is not a multiple of the stride
  is parsed as complete records; the trailing partial record is ignored and a
  malformed-peer-list warning is recorded. No slice ever runs past the packet.
- Our decision: at most 200 peers are accepted per response. Extra records are
  dropped after decoding.
- Our decision: peers with port 0, the unspecified address, multicast,
  broadcast, or an IPv4-mapped IPv6 form are dropped. Loopback, private and
  link-local peers are kept; LAN swarms are legitimate. Tracker targets are
  filtered separately (ADR 0003).

## IPv6

- BEP says: IPv6 announces use the same structure as IPv4 announces, including
  the same action number.
- BEP says: in an IPv6 response the stride of an address/port pair is 18 bytes
  (16-byte IPv6 address plus 2-byte port) instead of 6.
- BEP says: the 32-bit `IP address` field in the request is not usable under
  IPv6 and should always be 0.
- BEP says: the address family is determined by the address family of the
  underlying UDP packet; packets from a v4 address use the v4 format, those
  from a v6 address use the v6 format.
- BEP says: clients that resolve a hostname to both v4 and v6 and announce to
  both should use the same `key` for both, so trackers can match the two
  announces.
- Our decision: bind a v4 or v6 socket to match the chosen resolved address.
  One address family is used per announce attempt in v0.1; we do not announce
  to both families and do not implement multi-homed announces.
- Our decision: parse peers with a 6-byte stride on a v4 socket and an 18-byte
  stride on a v6 socket. The socket family, not the packet contents, selects
  the stride.
- Our decision: IPv6 peers are decoded and passed to the peer layer. The peer
  layer may not connect to them until its IPv6 work lands; decoding must still
  be correct and bounded.

## Errors

- BEP says: an error response has action `3`, the transaction ID, and a
  message string after offset 8.
- BEP says: on receiving an error packet, check that it is at least 8 bytes and
  that the transaction ID matches.
- Our decision: verify the transaction ID before treating action 3 as an
  error. A mismatched error packet is ignored and the wait continues.
- Our decision: the message is untrusted. It is passed through the same
  best-effort sanitizer as an HTTP `failure reason` before it may be shown in
  the UI, and it is never logged. Logs and errors record only a length and a
  classification. The attempt fails with `Rejected`.
- Our decision: an error packet is not retried within the same attempt; the
  state machine tries the next tracker or backs off.

## Scrape and extensions

- BEP says: scrape uses action `2` and can cover up to about 74 torrents at
  once; a full scrape cannot be done with this protocol.
- BEP says: the protocol has no version field or extension bits; clients and
  trackers should not assume a fixed packet size.
- Our decision: scrape is out of scope for v0.1. Only announce is implemented.
- Our decision: BEP 41 extension negotiation is out of scope. Extra bytes in
  connect and announce responses are ignored.

## Limits

Our decision:

| Limit | Value | Reason |
|---|---|---|
| Connect request | 16 bytes | BEP 15 layout |
| Connect response minimum | 16 bytes | BEP 15 check |
| Announce request | 98 bytes | BEP 15 layout |
| Announce response minimum | 20 bytes | BEP 15 check |
| UDP receive buffer | 4096 bytes | Fits 200 IPv6 peers (3620 bytes) |
| Peers per response | 200 | Bound memory and peer churn |
| Sends per attempt | 3 | Connect or announce; due at 0, 15, 45 s |
| Attempt deadline | 105 seconds; 2 seconds for `stopped` | Absolute from the first datagram; `stopped` is not retried |
| Connection ID age check | 50 seconds | Reconnect before a send; BEP allows 60 s |
| Connection ID reuse | within one attempt only | No cross-announce cache |
| DNS resolve timeout | 5 seconds | Bounds a stalled resolver |
| Transaction ID | 32 bits, OS random | BEP 15 asks for a random value |

## Test vectors

- Our decision: the connect request test vector is
  `00000417271019800000000012345678` (protocol ID, action 0, transaction ID
  `0x12345678`).
- Our decision: the announce request test vector uses a known connection ID,
  transaction ID, info-hash, peer ID, event and port, and asserts all 98 bytes.
- Our decision: the announce response test vector is action 1, transaction ID
  `0x12345678`, interval 1800, leechers 3, seeders 4, then
  `7f000001c8d5` (127.0.0.1:51413) and `000000000000`
  (0.0.0.0:0). The decoder must keep one peer and drop the invalid one.
- Our decision: additional tests cover a 15-byte connect response, a 19-byte
  announce response, a wrong transaction ID, a wrong action, an error packet,
  an IPv6 response with an 18-byte stride, and a peer section with a trailing
  partial record.
- Our decision: a paused clock with a connection ID 51 seconds old at a send
  proves that a new connect is sent before the announce, and that the announce
  is not sent with the old ID.
- Our decision: a paused clock proves that a UDP attempt is still running at
  60 seconds and fails only at the 105-second deadline.
- Our decision: the `tracker_udp_response` fuzz target feeds arbitrary bytes to
  the connect, announce and error decoders and asserts that no input panics or
  allocates unbounded memory.

## Known gaps

- Our decision: no scrape.
- Our decision: no BEP 41 extensions.
- Our decision: no multi-homed or dual-family announce.
- Our decision: no cross-announce connection-ID cache.
- Our decision: the retransmission schedule stops at `n = 2`, not `n = 8`.
  The state machine's backoff covers longer outages.

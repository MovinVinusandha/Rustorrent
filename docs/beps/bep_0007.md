# BEP 7: IPv6 tracker extension - announce notes

Status: planned for v0.1 (response decoding and `key`; no multi-homed or
dual-family announce).
Source: https://www.bittorrent.org/beps/bep_0007.html
Reviewed: 2026-11-25

This is a working summary in our own words, not a copy of the BEP. Each
statement is labelled "BEP says" (checked against the BEP 7 text) or
"Our decision" (an implementation choice that the BEP does not require).

## Announcing

- BEP says: an announce should be made for each local IP address that the
  client listens on, intends to publish, and can use as the source address of
  packets sent to the tracker (at least one address the tracker hostname
  resolves to).
- BEP says: each announce uses the corresponding local IP address as the
  source address of the connection, set with `bind()` before connecting.
- BEP says: this applies to TCP connections for HTTP and HTTPS trackers and to
  UDP announces for UDP trackers.
- BEP says: the client SHOULD include a `key` parameter in its announces.
- BEP says: the key should remain the same for a particular info-hash during a
  torrent session.
- BEP says: together with the peer ID, the key lets trackers identify a client
  for statistics when it announces from multiple IP addresses.
- BEP says: the key should have at least 32 bits of entropy.
- Our decision: v0.1 does not implement multi-homed announcing. One announce
  attempt uses one address family and one source address chosen by the OS; we
  do not bind to a specific interface or to a published address.
- Our decision: the family is the family of the tracker address chosen for
  the attempt. Resolution results are tried in the order the resolver returns
  them, up to 8 addresses. An address whose immediate `connect` or `send`
  fails is skipped; a timeout does not fall through to the next address,
  because the attempt budget is already bounded. See ADR 0003.
- Our decision: we do not announce to both IPv4 and IPv6 for one torrent. A
  dual-family announce is a later feature; the `key` design below already
  allows it without a protocol change.
- Our decision: `key` is a 32-bit value generated once per torrent session
  from OS randomness. The same value is sent in every HTTP and UDP announce of
  that torrent, for IPv4 and IPv6. It is not the peer ID and is not derived
  from it.
- Our decision: `key` is sent as an unsigned decimal integer in HTTP and as
  the 32-bit big-endian field in UDP. The value is stored as `u32` and is
  never sign-extended.
- Our decision: the key is regenerated when the torrent session is recreated,
  not on every announce and not on a tracker switch.

## IP announce parameters

- BEP says: an earlier version defined `&ipv4=` and `&ipv6=` parameters to
  announce an additional address of the other family.
- BEP says: those parameters are discouraged because they let an attacker
  announce a victim's IP address and trigger a DDoS against it.
- Our decision: we never send `ip`, `ipv4` or `ipv6` parameters, in HTTP or
  UDP. The UDP `IP address` field is always 0 (see BEP 15 notes).
- Our decision: an incoming parameter named `ip`, `ipv4` or `ipv6` in a
  tracker URL is ignored, not forwarded. The same applies to `key` and
  `peer_id` already present in the URL: they are removed and our values are
  sent instead.

## Response

- BEP says: when the tracker does not support compact responses, no change is
  needed; the original `peers` list can carry IPv6 addresses in string form.
- BEP says: when a compact response is requested, the tracker MAY add a
  `peers6` key.
- BEP says: `peers6` has the same layout as compact `peers`, but each endpoint
  is 18 bytes: a 16-byte IPv6 address and a 2-byte port, both in network byte
  order.
- BEP says: the example response is
  `d8:intervali1800e5:peers6:iiiipp6:peers618:iiiiiiiiiiiiiiiippe`.
- Our decision: decode `peers6` as an 18-byte stride. A length that is not a
  multiple of 18 decodes complete records and ignores the trailing partial
  record with a warning.
- Our decision: drop IPv6 peers with port 0, the unspecified address,
  multicast, or an IPv4-mapped form. Loopback, unique-local and link-local
  IPv6 peers are kept, for the same LAN reason as IPv4.
- Our decision: `peers` and `peers6` are decoded independently and merged.
  Each list is capped at 200 entries and the merged, deduplicated set is
  capped at 200. IPv4 and IPv6 addresses are distinct keys.
- Our decision: IPv6 peers are passed to the peer layer, which may not connect
  to them until its IPv6 work lands. Decoding must be correct and bounded
  before that.
- Our decision: a non-compact `peers` list may contain IPv6 literals. They are
  accepted on the same terms as IPv4 literals; hostnames are still dropped
  (see BEP 23 notes).

## Tests

- Our decision: a 36-byte `peers6` vector with two endpoints, `[::1]:51413`
  and `[2001:db8::1]:6881`, proves decoding and address formatting.
- Our decision: a 17-byte and a 19-byte `peers6` value prove that the partial
  record is ignored and the complete one is kept.
- Our decision: `::`, `ff02::1`, `::ffff:127.0.0.1` and port 0 are dropped.
- Our decision: a response with both `peers` and `peers6` proves the merge and
  the combined cap.
- Our decision: two announces of one torrent, one HTTP and one UDP, carry the
  same `key`; a new session carries a different one.
- Our decision: a request capture proves that no `ip`, `ipv4` or `ipv6`
  parameter is ever sent, even when the tracker URL already contains one.
- Our decision: the `tracker_http_response` fuzz target covers `peers6` and
  the combined decoder.

## Known gaps

- Our decision: no multi-homed announce and no per-interface bind.
- Our decision: no dual-family announce for one torrent.
- Our decision: no Teredo or transition-mechanism handling.
- Our decision: no IPv6 peer connection in v0.1; only decoding and storage.
